## Confirmed requirements

The user requires the main board to render pieces where they have been premoved, with red-shaded source and destination squares. The premove sequence must survive entering analysis and be reapplied on exit. This supersedes the original plan's clear-on-analysis-entry rule and its marker/preview-only presentation.

Reapplying the sequence to the display is distinct from committing moves. Actual moves still require the correct local turn and legal resolution against the actual live position. Recommendations below fill unresolved details; they are not user decisions. Q1–Q5 have been asked in this conversation; Q6–Q9 record further concrete choices exposed by source review.

## Reminder: what the current implementation does

| Context/action | Current implementation, before premoves |
| --- | --- |
| Actual versus selected position | `livePath` identifies actual play. `renderedPath` identifies the selected history/analysis node. At live they share position caches; merely copying a path does not create a safe speculative board |
| Press Analyse during live play | `enterInGameAnalysis` adds `PauseReason.Analysis`, freezes the actual clock and selects the actual live node with a detached rendered selector. Works for untimed games too. No premoved board currently exists |
| Explore inside Analyse | Both colours make ordinary legal analysis moves and navigate history while the actual live node stays fixed. New engine evaluations follow the selected analysis position |
| Opponent engine already thinking | Its existing search may finish. Its validated move is retained in `deferredPlayerMove`; it cannot play while Analysis owns the pause. The analysis engines are separate from the player engine |
| Press Exit analysis | Immediately select the actual live node, restore shared live selection, remove only Analysis ownership and resume timing if no other pause remains. Flush a retained player move, then arm the next eligible turn. No keep/discard prompt |
| Add Manual/Menu during Analyse | Those owners also block exploration. Removing Menu alone cannot remove Manual or Analysis. Restored paused analysis reconstructs both Analysis and Manual ownership |
| Browse history without pressing Analyse | This also uses a `LiveAnalysisFrom*` state, but without the Analysis pause. The clock keeps running. An already-armed player reply can advance the actual live path without moving the selected historical board; a successor turn is not armed until the live board is selected again |
| Make a move during history review | With takeback allowed, GameView asks to continue from that historical position and the store rewrites actual play. Otherwise it makes an analysis-only branch, with the configured stay/return-to-live behaviour |
| Press Takeback inside Analyse | If the game allows takeback, the action rewinds the **actual live node**, clears turn runtime and resets the rendered node/clock to the fallback, then reapplies the Analysis pause. It is not an analysis-only undo |
| Click an engine line | When playable, ordinary live play applies its first move as a real move; analysis plays the selected prefix as analysis moves; history uses the rewrite/branch policy. In the current working tree, `showLiveAnalysisMoves = false` leaves PV text visible but makes it read-only throughout a live game's contexts, including explicit analysis |
| Leave temporary analysis branches | A later real move from the same actual parent prunes its temporary descendants. This is an accepted existing policy; premove retention must not reopen the separate recording/branch-retention decision |
| Change players or edit the board | Reassignment is allowed during analysis and can remove a live seat, converting to free analysis. Direct board editing remains blocked inside live-game analysis |
| Timeout-ended analysis | Post-timeout exploration may remain available, but exiting it cannot restart live play or revive a pending turn |

## Conflict register and recommended handling

| Conflict | Recommended handling and implication |
| --- | --- |
| C01: displayed future pieces versus actual game | Introduce a pure display projection, distinct from actual/selected `IBoardPosition`. Red squares/displaced pieces never change game rules, side to move, check, clocks, engine FEN, captured tally, move tree or recorded analysis |
| C02: entering Analyse from a visually future position | Preserve the raw sequence and live anchor, cancel unfinished input, suspend queue execution, and explore from the actual live board. Hide red premove shading while exploring; keep a preserved-count label. Q1 |
| C03: exiting Analyse could look like bulk execution | Restore actual selection and reproject the remaining sequence. Resume actual moves only through the shared driver. Only one move executes per actual turn, regardless of how many pieces are already displayed ahead. Q2 |
| C04: opponent result ready before exit | Keep it bound to its original actual turn. After exit and final resume, commit that reply first, rebase the projection, then resolve the next due local intention. Do not validate the local intention against the pre-reply board or submit it to the opponent's turn |
| C05: Manual/Menu still pauses on exit | Show the restored projected pieces/red squares but keep execution suspended. Exit removes only Analysis ownership; a later Resume cannot restore Analysis or replay the sequence twice |
| C06: analysis moves look like edits to the queue | Keep their histories and object ownership independent. Undo/Clear on labelled preserved-queue controls may alter intentions; ordinary board/PV moves during Analyse only explore. No automatic queue replacement or promotion of an analysis branch. Q3 |
| C07: history review differs from Analyse | Preserve but suspend local intentions while showing historical pieces. Current clock and already-started engine completion retain existing behaviour. Revalidate on explicit return to live; do not execute a local premove unseen. Q4 |
| C08: two local queues compete for one board | Display one selected colour's projected sequence, labelled with a colour selector; retain both actual queues independently. Combining them requires rules for alternating order, speculative captures and conflicting occupied destinations. Q5 |
| C09: Takeback can change the anchor during Analyse | Keep analysis back-navigation separate from a clearly labelled actual-game Takeback. A real takeback clears both queues before changing paths; an analysis back-step preserves them. Do not restore old intentions solely because the new position happens to match. Q6 |
| C10: continuing from historical play rewrites the game | On the existing confirmed rewrite action, cancel both queues and the old turn before changing actual ownership. A cancelled confirmation or analysis-only branch preserves the suspended sequence. The branch-return preference never converts branch moves into intentions |
| C11: live PV/normal move competes with queued moves | An actual Play action must clearly use the actual board. Recommended: explicitly labelled Play now replaces that seat's unclaimed queue; Analyse/PV exploration never does. Do not validate a live PV against displaced squares. Keep the existing live move-target preference in this tranche; Q7 |
| C12: engine scores describe a different board from the picture | While projected pieces are shown, label evaluation as `Actual live position`; analysis mode evaluates the selected analysis board. Queue edits alone must not restart analysis or provide a speculative position to a player engine. Actual move recording captures only the actual parent output |
| C13: preserved sequence stored on a temporary branch | Store it in the game's runtime, with the actual continuation/seat as owner. Pruning the explored branch must not delete intentions. An identical coordinate move explored on a branch does not consume a queue entry |
| C14: navigation unmount accidentally destroys preservation | Keep committed intentions game-owned. Temporary menu/tab changes suspend them while gesture/playback owners are disposed. Return restores them over the current actual board; closing the tab or disposing/replacing the game cancels them. Q8 |
| C15: real moves invalidate the projected picture | Rebuild from the actual board after each actual commit. Show only a projectable prefix, mark the remaining unavailable rows and never resurrect a captured piece. Resolve/cancel the first due intention at its turn; do not silently skip it. Q9 |
| C16: stale drag, promotion, or delayed PV finishes after mode change | Analysis entry/exit, selected-colour change, queue editing and route change explicitly cancel unfinished input/playback before replacing its context. Preserve completed queued intentions, but do not accept a late click/drop as a new move |
| C17: actual result/seat/root changes during preservation | Timeout, rule-resolved end, resignation, accepted draw, actual reassignment, setup restart and root replacement cancel the sequence and drain its turn. No-op assignment or selecting another analysis node does not cancel it |
| C18: saving from a premoved or analysed board | Save the actual/selected canonical workspace as today, never the displaced layout/red squares/queue. A continued in-memory game may preserve its sequence; loading/restoring creates an empty queue. Show that premoves are temporary in queue help |
| C19: preview and warning highlights collide | Red fill identifies all pending sources/destinations; keep actual-last-move outline and selection/focus separate. Actual check stays a labelled live-state warning rather than a check calculated from a speculative king layout |

## Open questions

These are interaction questions, not approval requests. The first two change the analysis entry/exit experience; the remaining questions settle conflicts around preservation. Alternatives are recorded so a different answer can be implemented intentionally.

| ID | Question | Recommended answer and reason | Alternative/trade-off | Status |
| --- | --- | --- | --- | --- |
| Q1 | Should Analyse start from the actual live board or the displayed premoved board? | Actual live board; preserve/hide the queue. It provides a legal, known analysis anchor without inventing opponent replies | Analysing the displayed board requires defining its side to move, castling/en-passant rights and whether a one-sided speculative layout is legal. A separate explicit future-position analysis could be designed later | Asked; awaiting answer |
| Q2 | Should Exit analysis immediately resume actual play, or restore the display and wait for Resume? | Resume immediately if no other owner pauses, preserving today's exit contract; a ready opponent reply goes first | Requiring Resume gives time to inspect/change the restored sequence, but adds another paused state/action to today's exit flow | Asked; awaiting answer |
| Q3 | Can analysis edit or replace the preserved premoves? | Allow explicit queue Undo/Clear; exploration is independent. Append/edit projected pieces again after exit | Copy/replace from a two-colour PV needs a labelled conversion action and rules for ignoring hypothetical opponent moves; freezing all queue edits is simpler but less useful | Asked; awaiting answer |
| Q4 | What happens to intentions during ordinary history review? | Retain but suspend local execution until return. The clock/current engine reply still behave as today | Continuing unseen local moves changes game pacing; clearing loses prepared input simply for inspecting history | Asked; awaiting answer |
| Q5 | How should both local colours' queued pieces appear? | Show one selected colour's sequence with a White/Black selector; keep both queues | A combined board needs one future interleaving model and conflict rules. Supporting only one colour's queue reduces capability | Asked; awaiting answer |
| Q6 | Should Takeback inside Analyse remain an actual-game rewind, or mean analysis undo? | Provide separate analysis Back navigation and clearly label actual-game Takeback. Only the latter clears queues/rewinds actual play | Redefining Takeback by mode is possible, but changes the existing action; silently using it as premove undo is ambiguous | Open |
| Q7 | If a live engine suggestion/manual move is chosen while a queue exists, should it replace the queue or extend it? | An explicitly labelled Play now replaces that seat's unclaimed queue; only a premove action appends. In Analyse all ordinary input still explores | Implicit appending is convenient but can turn an intended immediate move into delayed input; preserving a queue after an alternative actual move risks stale dependencies | Open |
| Q8 | Keep intentions across menu/game-tab switches, or clear them on leaving the view? | Retain and suspend for the same in-memory game, including during analysis; clear on explicit tab close/game disposal | Clearing on every route change is simpler but breaks preservation when visiting Settings/Save during Analyse; background execution requires a separate policy | Open |
| Q9 | When the future projected suffix becomes impossible before it is due, discard it immediately or retain it marked unavailable? | Retain marked unavailable until its first due move is resolved/cancelled, but draw only a projectable prefix. Unknown replies can change future occupancy again | Immediate truncation gives a simpler picture but can discard a later move that would become possible before its turn | Open |
